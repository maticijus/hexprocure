# HexProcure v0.1.0 Review, 2026-10-20

Two independent reviews of `main` (identical to `feat/ai-roadmap` minus docs and the
lock file): a code and correctness review and a security review. Both ran as
read-only passes over the whole repository. Each finding was verified against the
code before it was kept. The three most severe were re-verified by the coordinator.

## Verdict

**Request changes before further production use.** Verification run on 2026-10-20
against a local Postgres 16: 207 of 207 Vitest tests pass, `tsc --noEmit` and
`eslint` are clean, coverage on domain + services + api is 86.6 % statements and
76.1 % branches. The domain layer is sound. The service and integration layers
have one critical correctness defect, one critical access-control defect, and a
cluster of HIGH defects around locking, matching, approval sequencing and
dispatch that together undermine the README's promises about double-spend safety,
sequential approval and reliable ERP delivery.

| | CRITICAL | HIGH | MEDIUM | LOW |
|---|---|---|---|---|
| Code review | 1 | 13 | 5 | 1 |
| Security review | 1 | 5 | 7 | 4 |

## Fix order

1. Security C1 (register as ADMIN), S2 (SQL injection), S4 (weak secret accepted). One short lane; closes the internet-facing chain.
2. Code C1 (order a requisition repeatedly) and code H6 to H11 plus S3 (matching bypasses, receipts over ordered, invoice approval double-send). One lane with a small concurrency test harness.
3. Code H12, H13 plus S5 (approval sequencing, self-approval, missing role matrix).
4. Code H2 to H5 and H14 (dispatcher claim, retry policy, connector fan-out, QBO data loss, recurring double-generation).
5. MEDIUM and LOW items.

Any AI lane that prefills invoices must not be merged into a production build until 1 and 2 are done. The LLM work itself (lane 1) is additive and can proceed on its branch.

## Code review findings

1. **[CRITICAL] One requisition can be ordered any number of times.** `src/lib/services/p2p.ts:194-275`, `src/lib/db/schema.ts:21-26,135`. `createPurchaseOrder` checks for APPROVED but never changes the requisition status, and there is no unique index on `purchase_orders.requisition_id`. A double click or API retry creates two POs, two reservations and two `PO_CREATED` events. Fix: add an ORDERED status, lock the requisition `FOR UPDATE`, set ORDERED in the same transaction, add a unique index.
2. **[HIGH] Dispatcher has no claim step.** `src/lib/integrations/dispatch.ts:25-30,47`. Plain SELECT then deliver; concurrent runs deliver the same event twice. The connector registry is also cleared and rebuilt per request. Fix: claim with `UPDATE … WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) RETURNING`, build the registry once, unique index on `qbo_sync_map.event_id`.
3. **[HIGH] Failing events retry forever and block the queue.** `dispatch.ts:28-30,58-63`. `retryable` is ignored, FAILED is never set, no attempt limit, always the oldest 100. Fix: set FAILED on non-retryable or attempt limit, add `next_attempt_at` with backoff.
4. **[HIGH] Only one connector per event type; CSV connector discards output.** `dispatch.ts:9-11`, `dispatch/route.ts:28-42`, `csv.ts:94-97`. Last registered wins, so a webhook silently disables QBO. CSV writes nothing. Fix: list of connectors per type with per-connector status; make CSV write or stop registering it.
5. **[HIGH] QBO marks events DELIVERED while the connection is down.** `qbo-connector.ts:42-45`. Events from an outage are lost. Fix: return `ok:false, retryable:true`; update `qbo-connector.test.ts:116`, which currently asserts the data-loss behaviour.
6. **[HIGH] Concurrent invoice approval sends two bills.** `p2p.ts:604-613`. No lock. Fix: `UPDATE … SET status='APPROVED' WHERE id=$1 AND status='MATCHED' RETURNING`, emit only when a row returns.
7. **[HIGH] Invoice-approved event has wrong currency and total.** `p2p.ts:619-625`. Currency hardcoded EUR; total ignores `amountMinor` for service lines; bigint SUM arrives as a string. Fix: PO currency, `COALESCE(amount_minor, quantity*unit_price_minor)`, cast to int.
8. **[HIGH] Invoice can bill a line from another PO.** `p2p.ts:442-450, 498-500`. Line query filters by id only. Over-invoicing checks on the other PO never see it. Fix: filter on `poLines.purchaseOrderId = po.id` in both places. (Same as security S3.)
9. **[HIGH] Match does not cap invoiced at received across invoices.** `src/domain/matching.ts:98-106`. 10 ordered, 5 received, two invoices of 5 both match. Fix: check `prior + quantity > received`.
10. **[HIGH] Repeating a PO line within one invoice skips cumulative checks.** `matching.ts:73-130`. Fix: running total per PO line while iterating; same for service amounts.
11. **[HIGH] Receipts can exceed ordered quantity.** `p2p.ts:328-364`. Duplicate `poLineId` in one request, or two concurrent receipts. Fix: lock the PO `FOR UPDATE`, merge or reject duplicate line ids.
12. **[HIGH] Approval sequence not enforced; steps of rejected requisitions stay actionable.** `p2p.ts:142-151`, `src/app/(app)/approvals/page.tsx:20-21`. Fix: require lower steps approved and requisition SUBMITTED; cancel open steps on reject; filter the inbox.
13. **[HIGH] Concurrent decisions strand a requisition or flip a rejection.** `p2p.ts:142-189`. Fix: lock the requisition first, or `UPDATE approvals … WHERE decision IS NULL RETURNING`.
14. **[HIGH] Recurring orders can generate twice.** `src/lib/services/recurring.ts:87-95,123`. The `FOR UPDATE` result is discarded and the pre-lock copy is used. Fix: select due templates `FOR UPDATE SKIP LOCKED` or re-check under the lock.
15. **[MEDIUM] Matching counts invoices of every status as invoiced; no void.** `p2p.ts:516-547`. Fix: count MATCHED and APPROVED only; add VOID status.
16. **[MEDIUM] PO cancel unreachable, `PO_CANCELLED` never emitted, cancelled POs still invoiceable.** `p2p.ts:301-320,433-437`. Fix: cancel route that emits the event; check PO status in `createInvoice`.
17. **[MEDIUM] Expected validation failures return 500; bad JSON returns 409.** `lib/api/helpers.ts:17-29,81`, `domain/approval.ts:58-83`, `domain/money.ts:13-20`, `requisitions/route.ts:58-62`. Fix: typed domain errors, map Postgres 23503 and 22P02 to 400, VALIDATION from `readJson`.
18. **[MEDIUM] Order templates accept unvalidated lines and generate EUR only.** `order-templates/route.ts:46-51`, `recurring.ts:33-62,109`. Fix: reuse requisition line validation; add currency to templates.
19. **[MEDIUM] Invoice parser misreads labels and decimal commas.** `invoice-parser.ts:10-11,22-28`. "Invoice Number: INV-2026-001" yields "Number"; "Rechnungsnummer: RE-1234" yields "snummer"; "12,5" parses as 12500 minor units; "1.234" parses as null. Fix: require a separator after the label; treat `,\d{1,2}$` as a decimal comma. Lane 1 should reuse a corrected shared amount parser.
20. **[LOW] No CHECK constraints; 32-bit integer money columns.** `schema.ts`. Totals above about EUR 21.4M fail with a 500; negative quantities are storable. Fix: CHECK constraints; consider bigint.

Open question: QBO `VendorRef` is sent as a name string where QBO expects a reference object. Unconfirmed, pending Intuit sandbox credentials.

### Done well (code)
Pure domain with strict Money; approval band resolver rejects overlaps and handles boundaries; outbox in the same transaction; budget row lock; invoice number unique per supplier via index mapped to a domain error; focused tests on price tolerance and service lines; central error mapping.

### Test adequacy
No concurrency tests anywhere. `vitest.config.ts` excludes `src/lib/integrations` from the coverage gate. One QBO test asserts data loss. Untested paths: ordering twice, duplicate PO lines in one receipt or invoice, invoiced above received across invoices, out-of-sequence approval, invoicing a cancelled PO, non-EUR invoices and service totals, dispatch failure and attempt limits, several connectors per event, 4xx mapping.

## Security review findings

Risk level HIGH. Not covered: online `npm audit` and `pip-audit` of the OCR sidecar (paddleocr 2.7.3, paddlepaddle 2.6.2, PyMuPDF 1.24.9). Run both with network access before release.

1. **[CRITICAL] Unauthenticated self-registration as ADMIN.** `auth/register/route.ts:8` passes the whole body to `registerUser`, which accepts `role` (`services/auth.ts:21,39`). The route is public. `POST /api/v1/auth/register {"email":"x@evil.io","password":"12345678","role":"ADMIN"}` yields an admin account. Fix: destructure only `name, email, password`; remove `role` from the input type; always insert REQUESTER; consider `ALLOW_SELF_REGISTRATION=false` for production.
2. **[HIGH] SQL injection with stacked statements in spend analytics.** `services/analytics.ts:21-22` interpolates `from` and `to` into `sql.raw`. No bind parameters, so pg uses the simple query protocol and accepts multiple statements. `?from=2020-01-01'::timestamptz; UPDATE users SET role='ADMIN' WHERE email='me@x'; --` rewrites the database. Fix: validate `^\d{4}-\d{2}-\d{2}$`, bind through drizzle's `sql` template, keep `sql.raw` only for the allowlisted group expression.
3. **[HIGH] Invoice lines can reference another PO's lines.** Same as code finding 8.
4. **[HIGH] Weak placeholder `AUTH_SECRET` passes validation.** `lib/api/helpers.ts:33` requires 8 characters; `.env.example` ships `change-me`. Sessions can be forged for any user id, and ids leak via attachment listings. Fix: require 32 characters, reject known placeholders, check once at startup, remove the unchecked `process.env.AUTH_SECRET!` uses in the QBO routes.
5. **[HIGH] Missing role checks and segregation of duties.** No role or ownership check in `submitRequisition`, `createPurchaseOrder`, `addReceipt`, `createInvoice`, `matchInvoiceById`, `sendPurchaseOrder`. `decideApproval` lets the requester approve their own requisition. One MANAGER can run the whole flow alone. Fix: reject self-approval, enforce sequence, define and enforce a role matrix in the services, correct the README.
6. **[HIGH] Rate limiting keyed on client-controlled `X-Forwarded-For`.** `request-guards.ts:7-10`. New bucket per request defeats the login limit and fills the key map. Fix: trust only the proxy-set header (`X-Real-IP`) or the right-most trusted hop; rate-limit login per email.
7. **[MEDIUM] Session cookie lacks `Secure`.** `lib/auth.ts:66` and the OAuth state cookie. Fix: add `; Secure` in production.
8. **[MEDIUM] Any user can email PO PDFs to any address.** `purchase-orders/[id]/send/route.ts:49-50`. Fix: restrict override to buyer or ADMIN, or to the supplier's domain.
9. **[MEDIUM] OCR sidecar has no auth and no page cap.** `services/ocr/main.py:50,58`. Fix: cap pages near 10, shared-secret header, non-root container.
10. **[MEDIUM] Upload bodies buffered before size check; outbound fetches have no timeout.** `attachments/route.ts:30,48`, `invoices/extract/route.ts:18,26`, `ocr-provider.ts:36`, `webhook.ts:29`. Fix: reject `content-length` above 11 MB before `formData()`, nginx `client_max_body_size 11m`, `AbortSignal.timeout(30_000)`.
11. **[MEDIUM] No security headers.** `next.config.ts`. Fix: HSTS, `X-Content-Type-Options: nosniff`, CSP with `frame-ancestors 'none'`; verify magic bytes on attachments.
12. **[MEDIUM] Attachments, PO PDFs and PO lines readable by every role.** `attachments/[id]/route.ts:101-103`, `attachments/route.ts:137-138`, `purchase-orders/[id]/pdf`, `lines`. Confirm intent; otherwise entity-level access checks.
13. **[MEDIUM] API tokens never expire, no scopes; sessions not revocable.** `api-tokens.ts:29-46`, `auth.ts:44-63`. Fix: `expiresAt` and scopes; per-user `sessionVersion` checked on each request.
14. **[LOW] Account enumeration** via scrypt timing and the "Email already registered" message. `services/auth.ts:51`.
15. **[LOW] Case-sensitive duplicate check on registration** returns 500 on a case variant. `services/auth.ts:29`.
16. **[LOW] `claude-fix` workflow** allows `Bash(npx:*)` and `Bash(git:*)` with `contents: write` on untrusted issue text; only an owner label starts it. Fix: drop `npx:*`, pin actions to SHAs.
17. **[LOW] Minor configuration.** `allowedOrigins` accepts `http://`; compose default DB password; webhook HMAC has no timestamp, so receivers cannot reject replays.

### Done well (security)
scrypt with per-user salt; timing-safe HMAC sessions with user reload per request; random API tokens stored hashed, shown once; CSRF origin check on all mutations with Bearer exemption only; OAuth state nonce bound to a cookie; AES-256-GCM token encryption with rotation; random UUID storage keys; MIME allowlist and 10 MB cap; generic 500s with server-side logging; no `eval`, no `dangerouslySetInnerHTML`, no `child_process`; no secrets in source or history; non-root app container; DB and OCR not port-published.

### Before adding an LLM-backed feature
- Close S1, S2, S4. Otherwise the LLM endpoint and its provider spend are reachable with ADMIN rights from the internet.
- Fix S3 and S5 first; LLM-prefilled invoices would automate the duplicate-billing path.
- Treat LLM output as untrusted input: integer minor units, PO-scoped line ids, structured-output schema, no tool calls, no auto-approve.
- Wrap OCR and supplier text as delimited data; never in system instructions; user confirms the draft.
- Minimise PII: redact IBAN and bank details unless needed; DPA with appropriate retention and region; never log prompts or responses; audit event per call with metadata only.
- Per-user quotas and a monthly cost cap, since the per-IP limit is bypassable.
- Outbound calls: URL and key from env only, `AbortSignal.timeout`, input size caps including a PDF page cap.
- Re-run `npm audit` and `pip-audit` online; audit the new SDK dependency.
